# gbos-x86 handoff

## Goal
Run the Googlebook `lapis` Android userspace on an i5-8365U (Whiskey Lake). That CPU lacks GFNI, AVX-VNNI,
SHA-NI, 256-bit VAES/VPCLMULQDQ, AVX-IFMA and AVX-512; the lapis binaries use them.

- 2026-11-16 **USB storage: preserve Android vold support for external USB while protecting the GBOS stick.** `hook.sh` resolves the detected GBOS stick partition to its parent disk and bind-mounts an empty stage0 `/dev` directory over that disk's sysfs block node before `switch_root`; this hides the whole stick (including both partitions) from Android's coldplug scan. The generic `voldmanaged=usb` fstab rule is retained when no GBOS stick is present or the device-specific mask succeeds; unresolved paths or mount failures keep the fail-closed rule removal. If neither safeguard can be applied, stage0 stops before Android. `tools/test_boot_tuning.sh` covers the boot-disk-only mask, external USB fstab eligibility, and fallback. This is host-test evidence only; Android coldplug and hardware storage mounting still need a boot test. No physical media or image was touched.

## 2026-11-18: Latitude 7320 tablet mode and rotation (analysis, then the fix; hardware-unverified)
- **Rotation lost on boot-9 (16:24), worked on boot-10 (16:35), kernel #61 both.** `sensor-trial.txt` boot-9:
  `mFixedToUserRotation=true`, `fixed-to-user-rotation` reads `default` and the display SettingsEntry has
  `mFixedToUserRotation=null`, although `rotation-policy.txt` had set `disabled` at 16:24:43. boot-10 keeps
  `mFixedToUserRotation=1` (disabled). Both boots' RotationLockHistory show a second `caller=LaptopController` entry:
  boot-9 at 16:24:44.330 (about 1.4 s *after* the policy command), boot-10 at 16:35:36.459 (about 2.6 s *before* it).
  Disassembly of `services.jar` (`DisplayRotation$LaptopController.refreshConfig`, called from `foldStateChanged`):
  in device state SLATE it calls `setFixedToUserRotation(1)` (disabled); otherwise, with `mIsPc` and LID_OPEN, it
  resets the user rotation to landscape and calls `setFixedToUserRotation(0)` (default, which is "fixed" on a PC).
  So the one-shot `cmd window fixed-to-user-rotation disabled` races every device-state callback (and will also be
  undone after any later lid/device-state change). The user's RotationLockTile toggles in boot-9 could not help while
  fixed-to-user was on. `services.jar` also reads `config.override_forced_orient` in `DisplayRotation.configure`
  (AOSP uses it to clear `mDefaultFixedToUserRotation`); a candidate deterministic fix, side effects not yet checked.
  boot-9's logcat starts at 16:24:45.9, so the event itself is not in logcat.
- **Device state comes from `desktop-services.jar` `DesktopDeviceStateProvider`:** TABLET (state 3, slate property 103)
  only when `InputManager.isInTabletMode()` (SW_TABLET_MODE) and lid open; otherwise OPEN/LID_OPEN. With no
  SW_TABLET_MODE source Android is never in tablet state, so LaptopController always locks rotation.
- **No tablet switch:** INTC1051 binds `intel_hid`; there is no INT33D6 ACPI device, so `intel_vbtn` (CONFIG=m) has
  nothing to bind. `intel_hid` auto mode gives SW_TABLET_MODE only for chassis types 31/32, and then only after the
  first 0xCC/0xCD notify ("switch event received" in dmesg); none of boot-8/9/10 has that line, and the chassis type is
  not logged. Untested candidate (no kernel rebuild): `options intel_hid enable_sw_tablet_mode=2` (VGBS at probe, so
  Android sees the initial state; `=1` creates the device on the first event, which Android misses).
- **Soft keyboard:** `DisplayContent.computeScreenConfiguration` counts every non-virtual ALPHABETIC device that can
  dispatch to the display, so the always-present i8042 keyboard (and, on these boots, the HP USB keyboard and
  2.4G receiver) keep `keyboard=qwerty`, and the IME stays hidden. `PhoneWindowManager.adjustConfigurationLw` only
  hides it via the lid state. Vendor `AT_Translated_Set_2_keyboard.idc` only sets `keyboard.builtIn = 1` and a
  ChromeOS backlight node; no IDC key ignores a device. Planned: a switch-driven helper that detaches `atkbd` via
  `/sys/bus/serio/devices/serioN/drvctl` (`none` / `atkbd`) in tablet mode, or sets `show_ime_with_hard_keyboard`;
  plus a hwdetect report of `/proc/bus/input/devices`, `capabilities/sw`, chassis type, the resolved
  `intel_hid` `enable_sw_tablet_mode`, and `getevent -qS` switch state from an Android-side service.

  - `hwdetect.txt` gained a tablet-switch section: chassis type, resolved `enable_sw_tablet_mode`, intel_vbtn, the

    bind_mode), intel_hid dmesg, and all of `/proc/bus/input/devices`.

    `TABLET_MODE=0` disables) replaces the one-shot `sensor_rotation_policy.sh`. Log: `logs/boot-N/tablet-mode.txt`

## 2026-11-15: Latitude 7320 sensor trial overlay
- The latest live boot logged `cannot create overlay` because `/new` was already
  read-only EROFS. The trial helper now uses a tmpfs mount under stage0's `/dev`,
  which stage0 moves into the new root. It logs the failing command and stderr,
  cleans up failed mounts where possible, and does not retry failures in the
  same boot. A real mount test exercises a read-only root and the `/dev` move
  inside an isolated privileged container; this is not a hardware boot.
- When the trial is selected, a separate read-only diagnostic records timed
  sensorservice and display snapshots. Before the 2026-11-15 Live test, the
  experimental range and mapping were unverified; snapshots alone do not
  guarantee that events are active.
- Inspection of the exact cached Android 17 partitions found the display-policy
  cause: `framework-res.apk` defaults `config_supportAutoRotation` to `true`,
  while `vendor/overlay/framework-res__lapis__auto_generated_rro_vendor.apk`
  overrides it to `false`. The Latitude-scoped policy RRO restores that boolean
  at higher priority, and a one-shot `cmd window fixed-to-user-rotation
  disabled` runs after boot completion to clear desktop mode's independent
  fixed-rotation default. Both are gated with the experimental HAL;
  `SENSOR_HAL=0` skips them.

## Done
- `isa-emu/isa_emu_core.c`: software versions of those instructions. 13,373 known-answer checks pass.
- **Kernel emulation** (new): `kernel/isa_emu_patch/`. #UD handler in `arch/x86/kernel/traps.c` calls
  `isa_emu_handle_ud()` (`arch/x86/kernel/fpu/isa_emu.c`), which decodes the instruction, runs the core on the
  saved xsave image, and advances RIP. Covers GFNI (SSE+VEX), AVX-VNNI(-INT8), SHA-NI, VAES-256, VPCLMULQDQ-256,
  AVX-IFMA. Boot param `noisaemu` disables it. Source tree is in docker volume `gbos-ksrc`; `apply.sh` applies the
  patch, `build.sh` does the incremental build (image `gbos-kbuild`, clang r584948c).
- Kernel image: `kernel/out_isa/bzImage` (sha256 in `bzImage.sha256`; rebuilt since, so recompute). Original kernel
  is `kernel/out/bzImage`. Modules: `kernel/out/modules/6.18.21-gbos-whl+/` (110, incl. i915, iwlwifi).
- `kernel/isa_emu_test/`: freestanding test. 16/16 pass on QEMU Skylake-Client; the stock kernel SIGILLs.
- `lapis/patched/init`: init with SHA-NI routine redirected to the scalar one (optional speed-up; not needed with the
  kernel emulation). `tools/patch_init_sha.py`.
- QEMU boots of lapis userspace (`lapis/qemu/`): the real first-stage `init` runs unpatched on the emu kernel.
  `run_b.py` hand-does first stage (mounts real erofs images from `lapis/parts/`, fake dm devices) then runs
  `/system/bin/init selinux_setup`. Reached: SELinux policy loaded and enforcing, second-stage init, ueventd,
  apexd (APEXes mounted), logd, lmkd, servicemanager, BoringSSL self-tests, vold. ~15M instructions emulated,
  **zero illegal-instruction deaths**.

  - *The kernel side.* KernelSU (tiann/KernelSU, GPL-2.0) is now part of our kernel: `kernel/kernelsu/apply.sh` links its sources into `drivers/kernelsu` (the way upstream's `kernel/setup.sh` does) and `kernel/configure_whl.py` sets `CONFIG_KSU=y` and `CONFIG_KSU_X86_PATCH_SYSCALL_DISPATCHER=y`. Upstream's own x86_64 build list (`kernel/build-all-x64.sh`) has `android17-6.18` with `clang-r584948c`, i.e. exactly our branch, so no porting was needed.
  - *Why the dispatcher option is not optional.* Since 6.9 x86 hardens the syscall path, and in 6.18 `arch/x86/entry/syscall_64.c` dispatches with a **switch statement** (`case nr: return __x64_##sym(regs);`), not through `sys_call_table[]` - the table is still there (for `trace_syscalls.c`) but is not used for dispatch. KernelSU's hooks patch that table, so on 6.18 they would silently do nothing. Upstream's answer (3.3.0+) is `CONFIG_KSU_X86_PATCH_SYSCALL_DISPATCHER`: it patches the `x64_sys_call` dispatcher itself at runtime (absolute jump to `my_x64_sys_call`, which then goes through the table), through the fixmap, so read-only `.rodata` is no problem. The alternative (the android-generic/kernel-zenith patches that add `X86_FEATURE_INDIRECT_SAFE` and a `syscall_hardening=off` cmdline) was **not** used: it needs two extra commits in the tree and a kernel source change for the same effect.
  - *The syscall tracepoint is enough.* The hooks are driven by the `sys_enter` tracepoint, which exists whenever `CONFIG_HAVE_SYSCALL_TRACEPOINTS` is set (x86 selects it unconditionally, `arch/x86/Kconfig:297`) - `CONFIG_FTRACE_SYSCALLS` is **not** needed (it only adds the ftrace syscall tracer). The tracepoint's regfunc (`syscall_regfunc`, `kernel/tracepoint.c`) sets `SYSCALL_WORK_SYSCALL_TRACEPOINT` in every task, and `syscall_tracepoint_update()` (`include/trace/syscall.h`) hands it to new tasks, so the hooks work for everything started after the kernel boots.

Gamma is concave, and R and B are much noisier than G (2 of 16 sites each, IR subtracted, then the colour matrix: B row 2.32, −0.80 G), so noisy R and B lose more than G and greys turn green. Simulated at σ_G ≈ 40 DN, the centre grey moved to U −3.6, V −2.4, growing in darker areas. The neighbourhood grows with total sensor gain: 5x5 up to 8x, 7x7 up to 16x, 9x9 above. Above 8x, colour is also faded towards grey across strong luma edges (up to 70% removed), which targets the purple/green speckle where the 4x4 window straddles an edge. The temporal luma threshold grows with √(gain/8), up to 2x (14 → 28).
